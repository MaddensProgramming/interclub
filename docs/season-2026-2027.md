## Changes implemented

- A shared season configuration selects Firestore year `2026` (the starting year), displayed as `2027` in the existing year-selector convention.
- The frontend's round results and last-update timestamp now follow the selected season. `/fullRound` chooses the latest scheduled match day for the current season, or round 11 for archives.
- D1–5 use eleven rounds and twelve pairing slots. D6 uses nine rounds, ten slots and four boards. Dates and pairings come from `Paringstabel` rows 4–14, columns A:J and X:AF.
- D6 rounds 5–9 map to shared match days 7–11. Team pages retain official local round numbers. The date document has an optional `datesByDivision` map, preserving archived date documents.
- 6J uses the explicit twelve encounters in the separate `6J` worksheet, rows 13–41. Its four real teams play six matches each; there is no 6J match in local round 9. Standings can display both encounters against the same opponent.
- Byes retain their pairing positions but do not become clubs, players, standings entries or result-overview matches.
- Results merge by division/series and round number, rather than array offsets. Wrong-season dates, malformed responses, missing opened rounds/encounters and HTTP failures reject the import before writes. An empty feed after opening is a successful no-op, preserving stored data.
- Annual metadata and player search indexes are refreshed on successful imports. Team and metadata writes are awaited; write errors propagate and the last-update timestamp is written last.
- Functions now target Node 22. Hosting points to the actual Angular output directory, `dist/interclub/browser`.
- The backend uses the Admin SDK with its Cloud Functions service account. Public database rules are not relaxed or deployed by the season commands.
- Before round one opens, a missing season is initialized once with calendars and public player lists. Existing season documents are preserved. The scheduler keeps its 15-minute interval, with a maximum of one running instance. Imports run from 20 September 2026 through 2 May 2027; outside that window the function exits without API/database access.
- FRBE's authoritative board points and match points are retained, including administrative decisions. Special half-point/zero and team-forfeit codes are handled explicitly; unknown result codes stop the import.

## Current source limitations

At inspection, `icdata` returned the correct 2026–2027 calendars, board counts
and Elo thresholds. The anonymous club/401 player list and venue/401 endpoints
also responded successfully. However, `anon/icseries?round=1` through `round=11`
returned `[]`; adding `idclub=401` did not provide results either. The current
FRBE site's JavaScript still references the same API endpoint, while its public
view presently exposes player lists, venues and contacts.

The public FRBE repository confirms this is expected before 14:00 Brussels time
on the round date. See [the deployment runbook](deploy-2026-2027.md) for the pinned
source and branch comparison. The previous empty-feed blocker was too strict and
has been replaced with a waiting state. The current live populated result feed
still needs verification after publication. Real initialization writes have
succeeded; the source lists contain 5,710 entries across 106 clubs and produce
5,708 unique player documents.

FRBE explicitly excludes 6J from its planning/results manager. This branch
prepares its calendar and displays a notice that results are not automatically
updated. It ignores regular-manager 6J results because those pairings cannot
represent the separate schedule. A separate official results source/manual
import is still required for 6J standings and player statistics.

## Regulation changes that do not require a results-browser implementation

The competition summary lists Elo thresholds D1–D6 of 2350/2200/2050/1950/1800/1700,
reduced board-order flexibility and an extra player-list update period. The
regulations specify up to three places of board movement for eight-player teams,
two for six-player teams and one for four-player teams. D1 has additional Elo
eligibility restrictions, and an accessibility exception permits certain team
switches. This repository displays results; it does not validate team selection.
No independent eligibility validator has been introduced. It continues using
FRBE's assigned ratings and submitted results.

The summary mentions 14 February for the extra registration period, but the live
API advertises 15–18 February. Do not hard-code a deadline from either without
FRBE clarification. Refreshing the player search index on each successful import
allows later list additions to appear.

## Build and validation

Use Node 22.23.3 (see `.nvmrc`) and npm. Angular CLI and TypeScript are local
dependencies; Firebase CLI 15.31.0 was installed on the development PC.

```powershell
npm ci
npm --prefix functions ci
npm run build:all
npm test -- --watch=false --browsers=ChromeHeadless
npm --prefix functions test
npm --prefix functions run preview:season
npm --prefix functions run check:source
```

The root `.npmrc` enables `legacy-peer-deps` because the existing ngx-toastr
20.0.5 release declares Angular 21 peers, while this repository uses Angular 22.
The available release has no newer compatible peer declaration. Builds and
tests pass with this setting; remove it once the upstream dependency supports
the Angular version used here. No broad dependency upgrade was made.

Validation completed on 27 September 2026: fresh `npm ci` installations for both
packages, production Angular build and Functions TypeScript build passed. Added
tests cover release times, restart, partial feeds and official result codes; see
the deployment runbook for the latest counts. The Angular build emits a
non-fatal initial-bundle budget warning (about 1.30 MB versus 500 kB).

`preview:season` is entirely offline. `check:source` performs read-only HTTP
requests and never initializes Firebase. `check:source -- --full` also prepares
club/player data and transformations. A `WAITING` result is not verification of
populated results. `check:published` verifies public reads of the new season and
blocks the season hosting commands until a completed-import marker exists.
